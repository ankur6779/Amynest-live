8. Abstract (indicative)

A computer-implemented system generates a personalised daily child-development routine from caregiver and child context using a rules-first deterministic generator and a subsequent deterministic intelligence pipeline implemented in application logic (not a language model). Inputs include age band, wake and sleep times, school windows, caregiver identity, outdoor-suitability class, meal constraints, and optional previous-day signals. A candidate schedule is assembled from age-band templates and meal banks, then processed by ordered software passes that apply country time-windows, weather and air-quality substitution, school-block exclusion, load and energy heuristics, timeline integrity, and dinner-to-sleep gap repair. A validation gate refuses delivery of a trust-invalid routine. An optional language-model module may draft a candidate schedule or additional meal-option names; any such draft enters the same deterministic pipeline and safety gate, and on failure the system falls back to rules-based generation. Concurrent-safe environmental detection on the client preserves an explicit caregiver weather choice against late-arriving geolocation results. Implemented client environments are a web application, an iOS native shell executing that web application, and an Android WebView shell. Wearable, voice-assistant, and on-device inference environments are described only as alternative or future embodiments.

This abstract does not assert novelty, patentability, or filing status.

1. Field of the Invention

The present invention relates to computer-implemented systems for generating personalised daily routines for a child in a family or caregiver setting. More particularly, it relates to deterministic, constraint-based schedule generation and subsequent software-pipeline processing that coordinate age and developmental constraints, meal and sleep timing, school hours, weather and air-quality context, country-specific time windows, previous-day completion signals, caregiver identity, and safety validation. The field includes optional machine-assisted content augmentation in which a language-model inference engine may propose candidate content that is then subjected to the same deterministic processing. The field is not limited to any particular language-model vendor.

2. Background of the Invention

Generating a coherent daily routine for a child is a multi-constraint computational problem. A usable schedule must simultaneously respect developmental age (including infant feeding structure), wake and bedtime, school attendance and travel, meal timing including a physiologically relevant dinner-to-sleep interval, outdoor suitability given weather and air quality, household diet and allergies, who is caring for the child that day, fixed appointments, and what happened yesterday (sleep quality, mood, completion). Static calendar templates do not adapt these constraints. General-purpose language models can emit fluent activity lists but do not, by themselves, enforce dinner-to-sleep geometry, country dinner windows, air-quality outdoor caps, or refuse an unsafe artefact. A technical system is required that (i) can generate a complete routine without calling a language model, (ii) can optionally accept a language-model draft, and (iii) in either case applies the same deterministic constraint, repair, and validation machinery before delivery.

A further technical problem arises at the client: automatic environmental detection (geolocation and meteorological lookup) is asynchronous. If a caregiver explicitly selects an outdoor-suitability value while detection is in flight, a late result must not overwrite that choice, and concurrent generate actions must not launch duplicate network lookups.

3. Objects of the Invention

  • To provide rules-based, deterministic generation of an age-banded daily routine as the primary production path.
  • To provide a deterministic intelligence pipeline, distinct from any language model, that applies ordered constraint, personalization-heuristic, and repair passes to a candidate routine.
  • To enforce age-dependent minimum dinner-end to bedtime gaps and country-specific dinner and sleep windows.
  • To enforce outdoor-duration and substitution policies from weather classification and, separately, from air-quality index (AQI) policy.
  • To refuse delivery (including HTTP 422 on applicable endpoints) of a routine that fails blocking trust validation.
  • To support optional language-model augmentation of a candidate schedule or meal-option names, always followed by the same pipeline and validation, with fallback to rules-based generation on failure.
  • To provide concurrent-safe environmental detection that preserves explicit caregiver preference and shares in-flight retrieval.
  • To incorporate previous-day and historical signals into subsequent generation without requiring neural-network training.
  • To operate on implemented clients comprising a web application, an iOS Capacitor web shell, and an Android WebView shell.

4. Summary of the Invention

In a primary embodiment, routine generation proceeds as:

Inputs → input resolution → deterministic / rules-based generation → deterministic intelligence pipeline (including dinner-anchor repair) → safety / validation → output (or rejection)

In an alternative embodiment, a language-model inference engine produces a candidate artefact that is then processed by the same deterministic intelligence pipeline and safety gate. If validation fails or the language-model call fails, the system falls back to rules-based generation. The language model does not execute the pipeline, does not guarantee safety, and is not required for generation.

According to a first aspect, a computational orchestration system comprises: (a) one or more client execution environments as implemented (web application; iOS native shell executing the web application; Android WebView shell) communicating with (b) a server-side engine exposing a typed application programming interface including at least POST /routines/generate (primary) and POST /routines/generate-ai (optional augmentation).

According to a second aspect, an ambient-condition classification module on the client performs concurrent-safe environmental detection using a synchronously readable reference and a deferred component-state flag (weatherTouchedRef / weatherTouched), a registry holding at most one in-flight detection Promise, mapping of meteorological parameters to an outdoor-suitability class (yes / limited / no, corresponding to suitable / limited / unsuitable), discard of late results if the caregiver touched the control, and injection of the class into the generation payload (weatherForCall) before user-interface state commit, including re-injection after a wake-time confirmation dialog.

According to a third aspect, a rules-based generator (generateRuleBasedRoutine) assembles a day from age-band templates using a date-seeded shuffle (dateSeed(date, childName)), meal banks, school and travel blocks, and caregiver bonding-density modulation.

According to a fourth aspect, a deterministic intelligence pipeline (runRoutineIntelligencePipeline), which is application logic and not a language model, applies ordered passes including family-intelligence preparation, behaviour signature, schedule / meal / weather / culture processing, emotion-adaptive polish, completion/freshness/autonomy, load balancing, energy heuristic, preservation of fixed and special items, timeline integrity, dinner-anchor repair, explainability metadata, and personalization-memory persistence. The scheduler is not re-run after the initial placement pass. Exclusive-infant paths (age 0 to less than 6 months) skip late polish passes except sleep/feeding validation.

According to a fifth aspect, dinner-anchor repair (repairDinnerAnchor) enforces a single dinner block ending at least a minimum gap before bedtime: 60 minutes if age is less than 48 months; 90 minutes if age is less than 156 months; otherwise 120 minutes; within a country-profile dinner window; with overlap repair and re-application.

According to a sixth aspect, a safety architecture distinct from language-model inference comprises at least: (i) enforceRoutineSafety combining AQI outdoor-duration enforcement and blocking trust validation (sleep anchor; dinner-before-bed for ages ≥ 36 months; infant feeding structure); (ii) a deterministic meal-option sanitizer; (iii) client-side caregiver simplification (simplifyForHandler); (iv) refusal to return or persist a trust-invalid routine (HTTP 422 on applicable routes). An optional advisory validator on a separate safety route is not the generate choke-point.

According to a seventh aspect, optional language-model augmentation drafts a candidate or meal-option names; output is processed by the pipeline and safety gate; providers are substitutable.

Wearable devices, voice-assistant interfaces, smart-home actuation, and offline/local-model inference are not present-tense implemented embodiments. They are disclosed only as alternative or future implementations in Section 6.18.

6. Detailed Description of the Invention

Function names, HTTP paths, and numeric thresholds below are taken from the production implementation (certified June 2026). They illustrate enablement. Compatible substitutions (other databases, other meteorological providers, other language-model providers, other client shells executing the same web application) do not depart from the architecture. Third-party services (including language-model APIs, Open-Meteo, browser geolocation, Capacitor, Android WebView, Firebase, RevenueCat) are infrastructure, not proprietary inventive elements.

As used herein, deterministic intelligence pipeline means ordered application logic (runRoutineIntelligencePipeline). It is not a language model, not a neural network, and not “AI generation.” Product marketing may use the word “intelligence”; this specification does not treat that word as synonymous with a language model.

6.1 System architecture (Figure 1)

Implemented client environments: (1) a web-browser application; (2) an iOS application implemented as a Capacitor native shell executing the same bundled web application; (3) an Android application implemented as a WebView wrapper loading the production web application. All three present the same routine-generation user interface. The server exposes POST /routines/generate (certified primary) and POST /routines/generate-ai (optional). A persistent data layer stores child profiles, routines, outcome/completion records, and personalization memory. Optional external services: a meteorological API (illustratively Open-Meteo; substitutable) and a language-model inference API (illustratively accessed via a JSON-chat helper; vendor-substitutable).

6.2 Input resolution

resolveRoutineGenerationInputs sanitizes and defaults wake, sleep, school start/end, outdoor class, mood, special plans, and fridge-inventory strings. Missing times receive safe defaults. The resolved structure is the input to both the rules-based generator and the pipeline wrapper runIntelligencePipelineOnItems.

Additional request context, not all of which is required, includes: child identifier and name, age in years and months, caregiver key (mom, dad, both, grandparent, babysitter), diet type, regional cuisine / food style, allergies, parent goals, school-meal mode, fixed activities, country code from the parent profile, and optional previous-day signals.

Age grouping used by the generator includes at least: infant (<12 months), toddler (<36), preschool (<60), early school (<120), and pre-teen. A feeding-focused grouping further distinguishes exclusive infant 0–6 months. A separate safety-library age-band classifier may be used on an advisory safety route; it is not the generate choke-point. PATENT COUNSEL: two classifiers exist; do not conflate them into a single named “engine” without specifying which path is claimed.

6.3 Concurrent-safe weather handshake (Figure 3)

Immediately before a generate request, if automatic detection is enabled and the caregiver has not touched the outdoor control, the client invokes ensureWeatherDetected.

  1. If weatherTouched or weatherTouchedRef is set, return the current user value.
  2. If an in-flight Promise exists in weatherDetectInFlightRef, await it (at most one detection).
  3. Otherwise start detectWeatherOutdoorFromBrowser: geolocation with configurable timeout (illustratively 5000 ms), then a meteorological query for temperature, precipitation, wind speed, and weather code.
  4. Map to yes / limited / no (suitable / limited / unsuitable): storms, heavy rain/snow, precipitation ≥ 2 mm, wind ≥ 40 km/h, temperature ≥ 40°C or ≤ 0°C → no; drizzle/fog/light precipitation, temperature ≥ 35°C or ≤ 5°C, wind ≥ 25 km/h → limited; otherwise yes.
  5. After resolution, if the ref is now touched, discard the detection and keep the user value.
  6. Thread the class as weatherForCall into the generate call before React state commit. On wake-confirm, re-inject from pendingAction.weatherForCall.
  7. Any exception (permission, timeout, abort, network) returns null; generation proceeds with the existing value.

A server-side generate occupancy semaphore (maximum concurrent generate slots) is an operational capacity control. It is not the client in-flight weather registry and is not required as a limitation of the weather claims.

6.4 Rules-based generation (Figure 2, Figure 4) — primary path

POST /routines/generate calls generateRuleBasedRoutine. This is the certified production generator. It does not call a language model.

The engine fills a time cursor from wake to sleep with mandatory anchors (hygiene, meals, school and travel where applicable, nap for younger bands, bedtime) and remaining slots from age-band activity pools. Pool order is randomized by a seeded shuffle dateSeed(date, childName) so the same date and name reproduce the same shuffle (the seed material in production is the child’s name concatenated with the date, not the numeric child identifier). Caregiver identity modulates bonding-density (extra bonding for both parents; substitute grandparent/babysitter reduces demanding outdoor/cooking and may force effective weather to limited). After template assembly, historical energy-profile reordering may run (applyEnergyCurveToItems; no-op unless sampleCount ≥ 3), then environmental enrichments (hydration/UV hints), then the deterministic intelligence pipeline.

If blocking fixed-activity conflicts exist and are not confirmed, generation returns without producing a routine. If the pipeline’s trust validation fails, the endpoint returns HTTP 422 and does not expose the artefact.

6.5 Deterministic intelligence pipeline (Figure 2)

runRoutineIntelligencePipeline is software. It does not invoke a language model. scheduleRoutineItems is not re-run after the initial placement pass. Late passes polish in place. Order implemented:

  1. prepareFamilyIntelligenceInput — trajectory, predictive hints, enrich previous-day context; computes a heuristic trustScore (bounded 0–100 from consistency/regulation trends and readiness; not a neural-network confidence).
  2. Build behaviour history from the outcome store using enriched context.
  3. deriveChildBehaviorSignature and deriveBehavioralState (country, day type, activity bias; optional reduce-study hint).
  4. Schedule / meals / weather / difficulty / culture / optimization / realism processing, including weather-driven activity substitution and AQI-aware outdoor policy in context.
  5. adaptRoutineForEmotion (uses caregiver-supplied mood and related state — not facial recognition).
  6. runAdaptiveCompletionPass (continuity → freshness → autonomy heuristics from history).
  7. applyDailyLoadBalancing.
  8. enforceEnergyCurve (heuristic evening downgrade distinct from historical peak/low window swaps).
  9. Preserve fixed activities and special-plan items.
  10. enforceFinalTimelineIntegrity including conflict resolution. Overlap resolution also runs inside earlier polish passes as a safety net, not as a second scheduler.
  11. Decision-enforced final pass.
  12. refreshExplainabilityMetadata (single parent-facing explainability pass).
  13. persistRoutinePersonalizationMemory and finalizeFamilyIntelligenceMoat.

Exclusive infant phase: isExclusiveInfantPhase is true when age in months is ≥ 0 and < 6. That path uses infant feeding/care assembly, sleep-boundary and overlap repair, and feeding/sleep trust validation; it skips late polish steps 5–12 except sleep validation, as implemented.

Dinner-anchor repair (Section 6.10) runs inside the pipeline (including re-run after overlap resolution, and after UAE outdoor hard-constraint when country is AE).

6.6 Weather-driven activity substitution

Outdoor items are identified by category and keyword tests. For class no (unsuitable), outdoor items are substituted with indoor equivalents. For limited, duration is reduced (illustratively halved on the AI-item weather adjustment tests) and indoor backup notes may be appended. For yes (suitable), items pass unless another constraint (AQI, UAE heat window, substitute caregiver) applies. Functions are non-mutating with respect to caller arrays (they return new item lists).

6.7 AQI (air quality) — distinct from weather

AQI is a numeric environmental input, not the three-class weather handshake. Categories (US EPA–aligned bands in code): ≤50 good; ≤100 moderate; ≤200 sensitive; ≤300 unhealthy; above 300 more severe. Hard outdoor duration caps from AQI: if AQI > 300, 0 minutes outdoor; if AQI ≥ 200, 15 minutes; if AQI ≥ 150, 20 minutes. AQI 150–200 is treated as exposure mode limited. Country culture profiles may further adjust exposure mode. Rainy-condition text may cap outdoor blocks at 10 minutes. enforceOutdoorDurationLimits trims or splits outdoor blocks. Language-model inference does not perform this enforcement.

6.8 Country-specific schedule windows

routine-country-profile.ts defines launch profiles. Implemented country codes: US, UK, AU, NZ, AT, AE, IN. Each profile includes wake, sleep, and dinner minute-windows, school-end range, and cultural intensity flags (extracurricular, outdoor, academic, independence) plus a meal-pattern label. These are configuration tables, not universal human truths.

Verified examples (clock times from code minute windows):

UAE outdoor hard constraint: outdoor activities starting before 18:30 are shifted into an evening window (enforceUaeOutdoorHardConstraint). Do not treat this 18:30 rule as applying to all countries.

6.9 Meals (Figure 4)

Default production source: deterministic meal banks keyed by diet family (vegetarian / eggetarian / non-vegetarian) and slot (breakfast, lunch, dinner, snacks, tiffin), further specialized by region. Selection uses the date+name seed and optional fridge-inventory interpolation (mealFromItems). Infant/toddler feeding uses age-feeding banks and on-demand feeding notes, not adult meal names.

Meal slots are anchored to wake/sleep/age (anchorMealSlots).

Optional augmentation: a focused language-model call may request a predetermined number of dish-name options per slot (illustratively exactly four in the enrich prompt). If the model returns fewer than four valid names for a slot, that slot is left unchanged. Instruction-like wording in a parent-supplied fridge list is treated as ingredient names in the prompt. Cross-slot variety and diet/allergy checks are applied by sanitizeMealOptionsInRoutineItems with priority Safety > Diet > Structure > Variety. Jain, vegan, vegetarian, eggetarian, pescatarian, gluten-free, and high-protein modes are encoded. Deterministic sanitizer treatment of Jain currently shares the vegetarian meat/egg exclusion branch; onion/garlic/root-vegetable Jain constraints are additionally stated in language-model diet prompts. PATENT COUNSEL: do not claim a deterministic regex root-vegetable filter unless later implemented; disclose prompt-level Jain rules as an embodiment of constrained generation.

6.10 Dinner-anchor repair (Figure 7)

getMinimumDinnerSleepGap(ageMonths): if age is null, 90 minutes; if < 48 months, 60 minutes; if < 156 months, 90 minutes; otherwise 120 minutes. repairDinnerAnchor ensures a dinner candidate exists (promoting an evening meal if needed, or inserting), places it in the country dinner window, and requires dinner end + minimum gap ≤ bedtime. After overlap resolution the repair is re-run. Dinner is required for applicable ages (dinnerRequiredForAge). Trust validation for ages ≥ 36 months includes dinner-before-bed. This geometry is certified production health policy, not a language-model output.

6.11 Safety architecture (Figure 6)

Safety is deterministic. Layers:

  1. Generate/partial-regenerate choke: enforceRoutineSafety = optional AQI outdoor clamp + runBlockingTrustValidation (sleep last/anchor, dinner-before-bed ≥36 months, infant feeding/age-safe meals). Callers must not return or persist when valid is false. Full pipeline endpoints may skip re-mutating AQI (skipAqiEnforcement) after the pipeline already applied AQI, then re-assert trust.
  2. Meal sanitizer as in 6.9.
  3. Client: simplifyForHandler removes skip-categories, caps activity count, and prefixes “Easy:” or “Step:” on non-essential activity titles for grandparent/babysitter — not a general rewrite of instruction notes.
  4. Optional advisory route: validateRoutine from a safety library, used by a separate HTTP safety endpoint / parent UI — not the generate choke-point.
  5. Partial regenerate is disallowed below 36 months (PARTIAL_REGEN_MIN_AGE_MONTHS); those ages must use full safe generation.

The language model does not guarantee safety.

6.12 Family intelligence and personalization (Figure 8)

Previous-day context may include sleep quality, mood score, and activity-completion percentage from the most recent signal, plus yesterday’s meal names and activity categories from the stored routine. On the optional language-model path these are inserted into the prompt. On the rules-first path they enrich pipeline context (freshness, completion, emotion, load).

Historical energy profile: peak-focus and low-energy windows derived from completion analytics. applyEnergyCurveToItems swaps at most one learning item into the peak window and one rest item into the low window when sampleCount ≥ 3; otherwise it is a no-op.

Learning weights: deterministic correlations of past behaviours and 14-day slot completion (computeLearningWeights), producing category weights in [−1, +1] and per-hour completion rates. These are personalization state. They are injected into the optional language-model prompt. This is not neural-network training.

Family-intelligence profile stores trajectory, personalization memory, predictive hints, and heuristic trustScore, then finalizes insights after the pipeline. Persistence is child- and date-scoped. If childId is absent, preparation is a no-op.

6.13 Optional language-model augmentation (Figure 5)

POST /routines/generate-ai may request a JSON schedule from a language-model inference engine using a structured prompt (profile, age-band guidance, caregiver, weather class, previous meals/categories, energy profile, learning weights, fridge, diet, allergies). The resulting items are energy-curved, weather-adjusted, passed through runIntelligencePipelineOnItems (the same pipeline), school-block sanitized, and enforceRoutineSafety. On trust failure the implementation throws and falls back to rules-based generation. Meal-option enrich is a separate optional model call (Section 6.9). No specific vendor is essential.

6.14 Fallback

(a) Language-model path validation failure → rules-based generation. (b) Exception on the rules path → emergency deterministic fallback generator which still applies dinner repair. (c) Weather detection failure → existing/default outdoor class. (d) Meal enrich parse failure → items unchanged for those slots.

6.15 Persistence and explainability

A generated routine is returned to the client for preview; persistence occurs on user save to the routines store. Parent-facing adaptation strings are finalized from pipeline traces (weather, energy, school, hydration). Explainability metadata is attached in a single late pass.

6.16 Regeneration

Full regeneration repeats Section 6.4 or 6.13. Partial regeneration of selected items is gated by age ≥ 36 months and must pass enforceRoutineSafety before overwrite; on failure the stored routine is left unchanged.

6.17 Caregiver adaptation

Implemented mechanisms: (i) template bonding-density and weather downgrade for substitutes; (ii) simplifyForHandler title prefix and category skip; (iii) caregiver-specific language-model prompt appendages on the optional AI path. The system does not implement a general post-hoc rewriter of all instruction notes for every caregiver.
