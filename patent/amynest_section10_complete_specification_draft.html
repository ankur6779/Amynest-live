1. Field of the Invention

P0 The present invention relates to computer-implemented child-development assistance systems. More particularly, it relates to the adaptive generation of child routines through hybrid processing comprising (i) deterministic rule-based orchestration and (ii) optional generative artificial-intelligence inference, together with environmental-condition integration, caregiver-adaptive computational transformation, asynchronous state coordination, and deterministic constraint/correction processing of generated routine artefacts.

Operative client execution environments disclosed for making and using the invention include a web-browser frontend execution environment and a native mobile frontend execution environment. Wearable, voice-assistant, and offline/local-inference environments are disclosed in the provisional as both multi-platform language and as future-proof embodiments (Form 2 §§6.1, 6.9, 6.10). Cross-platform parity is claimed for the ambient-condition classification function and the deterministic constraint/correction infrastructure to the extent those modules are present on a given client.

2. Background of the Invention

P0 The management of a child’s daily routine is a computationally and cognitively demanding orchestration problem. Existing digital tools — general-purpose calendar applications, static parenting schedule templates, and isolated rule-based scheduling utilities — exhibit at least the following technical limitations (Form 2 §2):

  1. Static environmental handling. Outdoor suitability is often entered manually. Omission yields a fixed default inconsistent with actual ambient conditions.
  2. Asynchronous environmental state conflicts. Systems that fetch environmental data typically initiate a fresh network query on each invocation, producing duplicate device-permission prompts, redundant computational requests, increased energy consumption, and concurrent asynchronous execution conflicts when multiple generation triggers fire in rapid succession.
  3. User-preference override risk. A late-resolving environmental detection can retroactively overwrite an explicit user choice made during the detection window, producing user-interface synchronisation latency and loss of caregiver control.
  4. Probabilistic generation errors. Outputs of a language-model inference engine may include developmentally inappropriate activities, activities during mandatory school hours, non-authentic dish names, incorrect dietary content, or repeated meal entries, unless a deterministic constraint/correction layer is applied.
  5. Excessive dependence on static input without machine-controlled contextual transformation when environmental, caregiver, or developmental context changes.
  6. Caregiver-oblivious instructions that do not adapt to the identity and capability profile of the active caregiver.
  7. Generic meal recommendations that ignore ingredient inventory, regional cuisine, dietary restrictions, or allergy parameters.
  8. Static activity ordering that does not adapt to a historically observed energy profile.

There is a need for a computational orchestration system and concurrent-safe scheduling architecture that (a) integrates real-time environmental data prior to schedule generation while preserving an explicit user choice; (b) suppresses duplicate network operations through shared in-flight retrieval state; (c) applies deterministic constraint/correction processing to generated artefacts, including probabilistic language-model outputs; (d) adapts instructions to the active caregiver; (e) produces region-aware, ingredient-aware, allergy-constrained meal options; and (f) may heuristically transform activity ordering according to observed energy profiles.

This background describes technical problems. It is not a prior-art search and does not assert that no prior art exists.

6.2 Environmental Detection and Synchronization

P0 A core inventive concept, and the strongest clearly enabled concurrent-processing mechanism in the 10 May 2026 disclosure, is the ambient-condition classification module (200), implemented as an asynchronous helper invoked by routine-generation trigger handlers immediately prior to the generation request. The module performs concurrent-safe environmental detection orchestration, explicit user-preference preservation, classification mapping, and direct payload injection (Form 2 §6.2; Figure 2; proposed Claims 1 and 5).

6.2.1 Preference Preservation

The module first evaluates an explicit user-preference preservation state flag implemented as a pair of cooperating data structures within the asynchronous state-management layer: a synchronously readable reference structure (211) and a deferred component-state structure (212). Both data structures are transitioned to a touched state when the user explicitly engages with an environmental selection control.

When either data structure indicates a touched state at invocation time, the module returns the user-selected value immediately without initiating any environmental query. This implements a respect-the-explicit-user-choice invariant and prevents user-preference override.

The cooperative use of a synchronously readable reference together with a deferred component-state structure addresses a known asynchronous-state-coordination problem: the deferred component-state structure may not yet reflect the latest committed value inside an asynchronous closure (a stale-closure condition), whereas the synchronously readable reference structure is authoritative within the same execution turn. The invention thereby provides explicit user-preference preservation in the presence of asynchronous state coordination (Form 2 §6.2.1; Claim 13).

A platform-agnostic helper atomically updates both the synchronously readable reference and the deferred component-state structures so that both sentinel values are updated atomically from the calling context’s perspective (Form 2 §6.9).

Implementation evidence (not a filing-date fact): in a web client this pair corresponds to a React state flag weatherTouched and a ref weatherTouchedRef in the routine-generation page.

6.2.2 Shared In-Flight Retrieval

A registry of pending asynchronous operations (220) holds at most one active environmental detection operation. When the module is first invoked in an untouched state, it assigns a new detection operation to the registry and may activate a user-interface indicator. Upon resolution or rejection, the registry entry is cleared and the indicator is deactivated.

If a second invocation occurs before the first detection resolves (for example, where the user triggers the generation control in rapid succession or where multiple generation-trigger pathways fire concurrently), the second invocation finds the registry populated and awaits the already-pending operation rather than initiating a second environmental query. Device permission dialogue and the upstream environmental query are each invoked at most once per generation session, providing duplicate-request suppression and reducing redundant computational requests (Form 2 §6.2.2; Claim 5A).

Implementation evidence: a module-level in-flight Promise weatherDetectInFlightRef. A server-side generate semaphore is a different mechanism and is not this registry.

6.2.3 Late-Resolution Race Handling

After the in-flight detection operation resolves, the module re-evaluates the synchronously readable reference structure of the explicit user-preference preservation flag before applying the detected classification. If the user has engaged the environmental selection control during the asynchronous resolution window, the flag is now in the touched state and the detected classification is silently discarded; the user-selected value is returned instead. The module therefore cannot retroactively override an explicit user preference that arose after the generation trigger fired (Form 2 §6.2.3; Figure 6).

6.2.4 Environmental Classification

On a web-browser execution environment, the module obtains device coordinates through a standard browser geolocation interface with a configurable timeout and a position cache. On a native mobile execution environment, the module obtains coordinates through a native location module that abstracts operating-system location services. In alternative embodiments, coordinates may be obtained from an on-device wearable sensor, a paired companion device, or a voice-assistant location-context provider (Form 2 §6.2.4).

The obtained coordinates are submitted to the remote meteorological data service (600) to retrieve environmental parameters including a standard weather-condition code, an ambient temperature value, a precipitation value, and a wind-speed value. A deterministic classification mapping function derives one of a fixed set of categorical outdoor-suitability classifications:

Condition (any one sufficient)Classification
Severe weather codes (thunderstorm, snow, rain showers, sustained rain); precipitation ≥ 2 mm; wind speed ≥ 40 km/h; temperature ≥ 40°C or ≤ 0°C“unsuitable” for outdoor activity
Moderate weather codes (drizzle, fog); precipitation > 0 mm; temperature ≥ 35°C or ≤ 5°C; wind speed ≥ 25 km/h“limited” — caution advised
All other conditions (clear, mainly clear, partly cloudy, overcast, calm)“suitable” for outdoor activity

The derived classification is threaded directly as a parameter through the generation call chain and inserted into the generation payload before a user-interface synchronisation cycle is permitted to commit any related state (direct payload injection (260)). This guarantees that the freshly derived classification reaches the orchestration engine even where the frontend has not yet committed corresponding state, reducing user-interface synchronisation latency (Form 2 §6.2.4; Claim 5B).

Where a routine-generation flow is suspended pending a confirmation dialogue (for example, a wake-time confirmation), the derived classification is captured in a pending-action closure and re-injected upon dialogue confirmation, providing continuity of the derived classification through asynchronous user-interface interruptions (Form 2 §6.2.4; Claim 3).

Implementation evidence: UI tokens may be labelled yes / limited / no while the computational classification remains suitable / limited / unsuitable. That mapping is an interface embodiment of the filed three-way classification P1.

Air-quality index (AQI) outdoor-duration caps (0 / 15 / 20 minutes) exist in current production (maxOutdoorMinutesFromAqi) and were not disclosed in Form 2. They are P2 and are not part of this §6.2 classification table. See Annex A.

6.2.5 Failure and Fallback

P0 The classification module catches exceptions including permission denial, network error, timeout, and abort signal, returning a null classification without rethrowing. On a null return the routine-generation flow proceeds with the existing user-selected or default value. The user is not interrupted by a detection failure; the orchestration is non-blocking (Form 2 §6.2.5; Claim 2).

6.4 Routine Generation Architecture

P0 The orchestration engine provides two routine-generation paths accessible via distinct interface endpoints (Form 2 §6.4; Figure 3).

6.4.1 Deterministic Rule-Based Generation

The rule-based path is a deterministic generation engine that selects activities from age-band-specific template pools. Inputs include the child age band, wake-up time, sleep time, school start/end times, mood, caregiver, environmental classification, parent goals, and ingredient inventory. The engine assembles a routine by sequentially filling a time cursor from wake to sleep, inserting mandatory anchor blocks (meals, hygiene, school where applicable, nap for toddlers, homework for school-age) and filling remaining slots from seeded-shuffled activity pools. The caregiver identity parameter modulates a bonding-density attribute — the number and type of caregiver–child joint activities inserted (Form 2 §6.4.1).

Form 2 describes this path as “zero-cost”. That phrase is an implementation characterisation, not a claim limitation.

6.4.2 Probabilistic / AI Generation

The generative path uses a language-model inference engine through a structured prompt. The prompt incorporates the child profile, date, age-band guidance, meal guidance, caregiver prompt, parent goals, mood context, observed energy profile, prior-day activity and meal categories, and the derived environmental classification (Form 2 §6.4.2). The language-model component is optional in the sense that the rule-based path of §6.4.1 is a complete generation embodiment without it. No vendor name (including any particular hosted model) is essential.

Language-model inference is probabilistic. The specification does not teach that a language model guarantees safety, developmental appropriateness, dietary correctness, or schedule consistency. Those properties, where obtained, are the result of deterministic constraint/correction processing and of the rule-based path.

6.4.3 Deterministic Constraint Processing

P0 Outputs of the language-model inference engine are post-processed through deterministic constraint/correction processing (330), which performs at least the following transformations (Form 2 §6.4.3; Figure 7):

  • Temporal anchoring: a time-cascade utility re-anchors activity start times to the actual wake-up time, correcting temporal drift.
  • Schedule-consistency enforcement (school-block exclusion): any activity item whose interval overlaps the child’s school start and end times is identified and rescheduled, preventing school-hour activities that are inconsistent with the stored school block.
  • Anti-repetition constraint: prior-day meal categories and top activity categories are passed to the prompt and cross-checked in post-processing to enforce variety across consecutive days.
  • Allergy and dietary filtering: items conflicting with the child’s allergy list or family dietary profile are removed and substituted from a deterministic safe-set.
  • Cuisine authenticity validation: generated dish names are validated against a regional canonical-name registry; non-conforming names are rewritten or replaced.
  • Cross-slot deduplication: the same dish name does not appear in more than one meal slot within the same daily routine.

Figure 3 of the provisional states that the deterministic correction layer is applied to both paths, with the AI path receiving the full chain. An embodiment therefore applies some or all of the above transformations to a rule-based artefact as well as to a language-model artefact.

The named production function sequence runRoutineIntelligencePipeline and the dinner-anchor repair repairDinnerAnchor with 60/90/120-minute gaps are P2. They may be argued as later implementations of “temporal anchoring” / “schedule-consistency” only with agent approval. They are not recited in the proposed priority claims. See Annex A.

6.4.4 Energy-Based Reordering

P0 Both paths may apply an energy-profile re-ordering step. The module reads the child’s historically observed energy profile (computed from stored routine-completion analytics) to identify a peak-focus window, a low-energy window, and a calm wind-down window. Cognitively demanding activities are shifted toward the peak-focus window; rest, sensory, and free-play activities toward the low-energy window; story time and bonding activities toward the calm window. Re-ordering is applied only when a minimum sample count of observations is available; otherwise the existing order is preserved (Form 2 §6.4.4).

Implementation evidence: a minimum sample count of three observations is used in current analytics code. The number “3” is not in Form 2 (which says “a minimum sample count”). Reciting “three” in a claim is P1 at most; safer to keep “a predetermined minimum sample count”.

This energy-profile processing is a deterministic heuristic over stored completion analytics. It is not a trained neural-network model and is not described as autonomous machine learning.

6.5 Environmental Activity Transformation

P0 Referring to Figure 5, the orchestration engine applies an environmental-state-driven substitution function (370) to generated routine items (Form 2 §6.5). Outdoor activities are identified by (i) an exact category match against a configurable outdoor category set, and (ii) a regular-expression test against a configurable outdoor keyword list (including, without limitation, park, playground, cycling, walk, garden, swim, run, jog, football, cricket, tennis, skating, fresh air).

For an “unsuitable” classification, outdoor items are substituted with pre-defined indoor equivalents from a deterministic lookup table, with replacement notes explaining the substitution. For a “limited” classification, outdoor items are retained but their duration is reduced and an indoor backup note is appended. For a “suitable” classification, items are returned unchanged. The function is pure and non-mutating, providing referentially transparent behaviour suitable for concurrent-safe execution.

UAE-specific outdoor timing rules in current production are P2 and are not described here as priority subject-matter.

6.7 Meal-Option Enrichment

P0 After the primary routine is generated, the orchestration engine may apply a two-phase meal-option enrichment engine (340) (Form 2 §6.7; Figure 4).

Phase A — Meal slot anchoring: ensure the routine contains correctly timed and labelled meal slots (Breakfast, Morning Snack, Lunch, Evening Snack, Dinner, Tiffin as applicable) consistent with the child’s age band and wake/sleep windows. Slot anchoring is also inherent in the rule-based path of §6.4.1, which inserts mandatory meal anchor blocks.

Phase B — Generative meal-option generation: a focused secondary call to the language-model inference engine produces a predetermined number of distinct meal-option names per meal slot. The enrichment prompt is parameterised by (a) family food style (vegetarian, non-vegetarian, vegan, Jain), (b) regional sub-cuisine, (c) parent-supplied ingredient inventory (treated strictly as ingredient names; instruction-like wording within the inventory is sanitised), (d) allergy list, and (e) the child’s age band (portion sizes and texture guidance).

Where an ingredient inventory is supplied, the enrichment prompt instructs the model to construct dish names by interpolating the supplied ingredients (for example, input “Paneer, Tomato” → output “Paneer paratha with tomato chutney”). The regional cuisine constraint governs cooking style; the ingredient list takes priority over regional bank suggestions. A deterministic deduplication step ensures the same dish name is not selected for more than one meal slot. The client presents enriched options as a selectable list.

Form 2 Claim 10 recites regional cuisine selected from a set comprising at least North Indian, South Indian, Bengali, Western, Asian, and Pan-Indian, with a region-specific description of canonical dishes incorporated in the prompt.

Meal banks as default production mechanism are P2 as a “default”. Form 2 already discloses deterministic template pools and meal anchors on the rule-based path (§6.4.1) P0. What was not disclosed is that deterministic meal banks are the primary production default and that “exactly four language-model options per slot” is not always the default. This Complete Specification therefore: (i) keeps Phase B as an optional generative enrichment embodiment as filed; (ii) does not claim “exactly four options” as essential; (iii) does not insert later meal-bank catalogues, country dinner windows, or sanitizer tables into the priority narrative. A dependent claim that meal names may be selected from deterministic template pools (without a language model) is P1 from §6.4.1 — see proposed Claim 15.
Jain / dietary logic — P1 claim-scope flag. Form 2 §6.7 and Claim 11 disclose Jain constraints as prompt constraints: exclude root vegetables in addition to meat, fish, and eggs, and exclude onion and garlic from suggested options. Figure 4 likewise shows “Jain → exclude meat · fish · eggs · root veg + exclude onion · garlic”. Current production encodes the same Jain root/onion/garlic rules in language-model prompt text (artifacts/api-server/src/routes/routines.ts). The deterministic meal-option sanitizer treats the Jain branch analogously to vegetarian for meat/fish/egg detection and does not implement a separate root-vegetable parser. Do not claim a deterministic Jain root-vegetable enforcement engine on the 10 May priority date. Claim 11 should remain prompt-constrained, or be omitted / rewritten with agent direction.

6.11 Technical Effects

The following technical effects are disclosed in Form 2 (abstract, §2, §3, §6.2, note on Section 3(k)) and are presented as engineering consequences of the architecture, not as a legal conclusion of patentability:

  • reduction of redundant computational requests and suppression of duplicate network operations and duplicate device-permission prompts;
  • minimisation of concurrent asynchronous execution conflicts through a single in-flight environmental retrieval;
  • preservation of an explicit caregiver environmental preference in the presence of late-resolving asynchronous detection (stale-closure-safe dual-state flag);
  • reduction of user-interface synchronisation latency by direct payload injection of the classification before a UI state-commit cycle;
  • continuity of a derived classification through an asynchronous confirmation dialogue via a pending-action closure;
  • non-blocking degradation: detection failure yields a null classification and generation proceeds on an existing or default value;
  • deterministic schedule consistency: wake-time temporal anchoring and school-block exclusion applied by machine to generated artefacts;
  • environmental-state-driven computational substitution of outdoor activities according to a three-way classification;
  • deterministic post-processing of probabilistic language-model outputs (allergy/cuisine/dedup/anti-repetition);
  • day-to-day variation with reproducibility via a date-and-child-identifier-seeded shuffle;
  • referentially transparent (pure, non-mutating) environmental substitution suitable for concurrent-safe execution.

8. Abstract

Proposed Form 2 abstract. Target: not more than 150 words (Patents Rules, 2003, as commonly applied). Word count of the following paragraph: 139 words.

A computational orchestration system generates adaptive child-development routines using environmental-state synchronisation and hybrid generation. Before generation, an ambient-condition classification module evaluates an explicit user-preference flag implemented as a synchronously readable reference and a deferred component-state structure. If untouched, concurrent invocations share one in-flight geolocation and meteorological retrieval. Returned weather-code, temperature, precipitation and wind parameters are mapped to a suitable, limited or unsuitable outdoor classification and injected into the generation payload before a user-interface synchronisation cycle. A late-resolving detection is discarded if the flag becomes touched during the asynchronous window. A hybrid engine provides a deterministic rule-based path and an optional language-model path. Deterministic constraint processing applies temporal anchoring, school-block exclusion, allergy filtering, cuisine validation and meal-slot deduplication. Technical effects include duplicate-request suppression, preference preservation under asynchronous resolution, and reduced interface synchronisation latency. Language-model vendor identity is not a limitation.
